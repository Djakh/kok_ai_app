# KOK.AI Mobile ↔ Backend Contract

Version: 1.0 draft  
Mobile implementation date: 2026-08-15  
Base path: /api/v1  
Status: required for backend implementation; real Kindwise integration has not yet been end-to-end tested

Backend implementation, provider mapping, data model, security, operations, and complete-feature requirements are defined in:

- docs/KOKAI_BACKEND_KINDWISE_IMPLEMENTATION_SPEC.md

## 1. Mobile workflow summary

The mobile client:

1. Guides the user through whole-tree, leaf, bark, flower/fruit, and additional photographs.
2. Collects foreground GNSS samples for about 12 seconds and sends the calculated coordinate plus quality evidence.
3. Uploads the categorized photographs to the KOK.AI backend for normalized species analysis.
4. Preserves the complete AI candidate list while allowing the user to confirm, correct, or mark the species unknown.
5. queries for nearby trees within 20 metres.
6. Requires the user to review possible duplicates.
7. Creates the tree with a stable client-generated idempotency key.
8. Reads the new tree through list, map, detail, and scan-history endpoints.

Kindwise is never contacted by the mobile application. The analysis provider is an implementation detail behind the KOK.AI backend.

## 2. Endpoint list

| Method | Path | Purpose |
|---|---|---|
| GET | /health | Deployment health; normally outside the /api/v1 prefix |
| POST | /api/v1/tree-analyses | Multipart photo upload and normalized AI analysis |
| GET | /api/v1/trees/nearby | Location-first duplicate candidates |
| POST | /api/v1/trees | Idempotent tree creation |
| GET | /api/v1/trees | Paginated list for Home, My Trees, and Map |
| GET | /api/v1/trees/{tree_id} | Full tree detail |
| GET | /api/v1/trees/{tree_id}/scans | Scan history |
| POST | /api/v1/trees/{tree_id}/scans | Future add-scan path |

Successful payloads may be returned directly or in the existing repository envelope:

~~~json
{
  "success": true,
  "data": {}
}
~~~

The existing ApiClient already unwraps that envelope. The backend should use one style consistently.

## 3. Authentication expectations

- All /api/v1 endpoints except explicitly public health checks require Authorization: Bearer {access_token}.
- The existing client refreshes once after a 401 through POST /api/v1/auth/refresh.
- Tree ownership is derived from the token, never accepted from owner_id in a create request.
- Image URLs may be short-lived authenticated URLs. If so, their expiry and refresh strategy must be documented.
- A 403 means the session is valid but the caller lacks access; 401 means refresh/sign-in is required.

## 4. Multipart analysis request

POST /api/v1/tree-analyses

Headers:

- Authorization: Bearer {access_token}
- Idempotency-Key: tree-{draft_id}-analysis
- Content-Type: multipart/form-data; boundary generated by the client

Repeated parts:

| Field | Type | Required | Notes |
|---|---|---|---|
| photos | file[] | yes | At least whole_tree and leaf |
| photo_types | string[] | yes | Repeated in the same order as photos |
| location_evidence | JSON string | yes | Schema in section 6 |

The Dart client sends one photos part followed by its corresponding photo_types entry for every local photo. The backend must validate equal counts and preserve category association. A future contract may use structured part names, but both teams must change together.

## 5. Photo-type values

| Value | Requirement |
|---|---|
| whole_tree | required |
| leaf | required when available; required by current mobile validation |
| bark | strongly recommended |
| flower_or_fruit | optional |
| additional | optional and safe fallback for an unknown future enum |

The backend must not infer type from filename or upload order alone.

## 6. Location-evidence payload

~~~json
{
  "latitude": 41.299503,
  "longitude": 69.240098,
  "horizontal_accuracy_meters": 5.8,
  "accepted_sample_count": 8,
  "rejected_sample_count": 2,
  "capture_duration_ms": 12000,
  "best_sample_accuracy_meters": 4.2,
  "captured_at": "2026-08-15T05:00:12.000Z",
  "quality": "acceptable"
}
~~~

Validation:

- latitude: -90 through 90.
- longitude: -180 through 180.
- accuracy values: finite and greater than zero.
- accepted_sample_count: normally at least 3.
- quality: excellent, acceptable, or poor.
- The backend stores the numeric evidence. It must not recompute a more precise claim from rounded display values.
- The UX thresholds are configurable mobile categories: excellent ≤5 m, acceptable >5 m and ≤10 m, poor >10 m. They are not scientific guarantees.
- Coordinates are explicit request fields; the backend should strip or ignore unnecessary image EXIF location metadata.

## 7. Normalized AI response

HTTP 201 or 200:

~~~json
{
  "id": "analysis_01J5ABC",
  "provider": "kindwise_plant_id",
  "analyzed_at": "2026-08-15T05:00:25.000Z",
  "candidates": [
    {
      "id": "candidate_1",
      "common_name": "Oriental plane",
      "scientific_name": "Platanus orientalis",
      "confidence": 0.87,
      "genus": "Platanus",
      "family": "Platanaceae",
      "description": "A large deciduous tree...",
      "representative_image_url": "https://cdn.example/species/1.jpg",
      "image_source_url": "https://licensed-source.example/item/1"
    }
  ],
  "health": null
}
~~~

Rules:

- confidence is normalized to 0.0–1.0.
- candidates are sorted highest confidence first.
- candidates may be empty for no confident identification.
- provider is attribution, not a credential or raw provider response.
- provider-specific JSON is not exposed.
- analyzed_at is UTC ISO 8601.

## 8. Species candidate schema

| Field | Type | Nullable | Notes |
|---|---|---|---|
| id | string | no | Stable within the analysis; submitted on tree creation |
| common_name | string | yes | Locale-specific value when available |
| scientific_name | string | no | Use "Unknown species" only if the provider truly supplied no taxonomy |
| confidence | number | no | 0.0–1.0 |
| genus | string | yes | Normalized taxonomy |
| family | string | yes | Normalized taxonomy |
| description | string | yes | Sanitized, provider-licensed content |
| representative_image_url | string | yes | Only when display rights permit |
| image_source_url | string | yes | Required when source attribution/licensing requires it |

## 9. Optional health schema

Health must be absent or null unless the backend actually requested and received health information.

~~~json
{
  "status": "possible_issue",
  "confidence": 0.64,
  "summary": "Visible leaf discoloration was detected."
}
~~~

The backend must not derive "healthy" from verification, approval, or registration status. The UI labels this as optional automated information and not a professional diagnosis.

## 10. Nearby-tree request and response

GET /api/v1/trees/nearby?latitude=41.299503&longitude=69.240098&radius_meters=20

HTTP 200:

~~~json
{
  "items": [
    {
      "tree_id": "tree_01J5XYZ",
      "display_name": "Library plane",
      "scientific_name": "Platanus orientalis",
      "image_url": "https://cdn.example/trees/tree_01J5XYZ/primary.jpg",
      "distance_meters": 4.3,
      "horizontal_accuracy_meters": 6.1,
      "registered_at": "2026-07-20T10:30:00.000Z"
    }
  ]
}
~~~

The server:

- Uses a geospatial index and calculates distance server-side.
- Returns nearest first.
- Does not automatically merge records.
- May apply authorization/privacy rules to images and exact coordinates.
- Supports a maximum radius enforced server-side.

## 11. Tree-creation request and response

POST /api/v1/trees

Headers:

- Idempotency-Key: tree-{draft_id}-create

Request:

~~~json
{
  "analysis_id": "analysis_01J5ABC",
  "selected_candidate_id": "candidate_1",
  "manual_scientific_name": null,
  "location_evidence": {
    "latitude": 41.299503,
    "longitude": 69.240098,
    "horizontal_accuracy_meters": 5.8,
    "accepted_sample_count": 8,
    "rejected_sample_count": 2,
    "capture_duration_ms": 12000,
    "best_sample_accuracy_meters": 4.2,
    "captured_at": "2026-08-15T05:00:12.000Z",
    "quality": "acceptable"
  },
  "duplicate_check_status": "noNearbyTrees",
  "nickname": "Library plane",
  "notes": "Near the north entrance",
  "visibility": "public"
}
~~~

duplicate_check_status currently uses the Dart enum names:

- noNearbyTrees
- possibleMatches
- skippedDueToNetworkFailure

Exactly one identification choice is expected:

- selected_candidate_id for an AI candidate;
- manual_scientific_name for a user correction;
- both null for unknown.

The analysis record and full candidates remain immutable. A correction is stored separately.

HTTP 201 returns the full tree-details schema from section 13. A repeated request with the same idempotency key and identical authenticated principal returns the original successful result.

## 12. Tree-list pagination

GET /api/v1/trees

Query:

| Name | Type | Notes |
|---|---|---|
| cursor | string | Opaque next_cursor from the previous page |
| limit | integer | Mobile sends 20; Home sends 5; Map may request up to 200 |
| q | string | Search nickname, common name, and scientific name |
| sort | string | newest, nearest, or last_scanned |
| species | string | Optional normalized species filter |

Nearest sorting requires latitude and longitude in a future contract revision or a server-known user position. If unsupported, return 400 with unsupported_sort rather than silently returning newest.

## 14. Scan-history contract

GET /api/v1/trees/{tree_id}/scans

~~~json
{
  "items": [
    {
      "id": "scan_01J6AAA",
      "scanned_at": "2026-09-15T08:00:00.000Z",
      "summary": "Follow-up visual scan",
      "image_url": "https://cdn.example/scans/scan_01J6AAA.jpg"
    }
  ]
}
~~~

POST /api/v1/trees/{tree_id}/scans should eventually accept categorized photographs, optional location evidence, and an Idempotency-Key. The current mobile UI deliberately does not submit this endpoint. Selecting "This is the same tree" preserves the draft and explains that scan creation is pending.

## 15. Error response and HTTP statuses

All non-2xx responses:

~~~json
{
  "success": false,
  "error": {
    "code": "ai_provider_unavailable",
    "message": "Tree analysis is temporarily unavailable.",
    "details": {
      "retry_after_seconds": 30,
      "field_errors": null
    },
    "request_id": "req_01J5ERR"
  }
}
~~~

| HTTP | Stable code examples | Mobile behavior |
|---|---|---|
| 400 | validation_error, unsupported_sort | Correct input |
| 401 | unauthorized | Refresh once, then sign in |
| 403 | forbidden | Explain access restriction |
| 404 | tree_not_found, analysis_not_found | Return to list |
| 409 | idempotency_conflict, possible_duplicate | Preserve draft and review |
| 413 | upload_too_large | Ask user to replace/reduce image |
| 415 | unsupported_image | Identify invalid photo slot |
| 422 | low_confidence, invalid_location_evidence | Review/retry |
| 429 | ai_quota_exceeded, rate_limited | Retry after supplied delay |
| 502 | ai_provider_unavailable | Retry without losing draft |
| 503 | backend_unavailable | Retry without losing draft |
| 504 | request_timeout | Retry with the same idempotency key |

Do not leak raw provider errors, credentials, upstream URLs containing secrets, or provider request bodies.

## 16. Idempotency behavior

- The mobile draft owns one stable base key.
- Analysis uses the base key plus "-analysis".
- Creation uses the base key plus "-create".
- Keys persist across application interruption and network retry.
- The server scopes records to authenticated principal, method, and route.
- Store the request fingerprint and completed response for at least 24 hours.
- Same key plus same request returns the original status/body.
- Same key plus materially different request returns 409 idempotency_conflict.
- Timeouts after server commit must be safe to retry.

## 17. Nullable-field behavior

The UI supports null for common name, genus, family, description, representative images, source links, optional health, last scan, confidence on manual/unknown records, notes, nickname, and image URLs. Use JSON null or omit optional fields consistently. Do not return the strings "null", "-", or "N/A".

Required identifiers, coordinates, dates, and scientific_name on a species candidate must not be null. A tree itself may have no confirmed scientific name when registered as unknown.

## 18. Image upload restrictions

Backend acceptance targets:

- MIME: image/jpeg, image/png, image/heic when the server can normalize it.
- Reject unsupported MIME with 415 unsupported_image.
- Maximum 10 MB per original file and 30 MB total request unless backend infrastructure sets a lower documented value.
- Maximum five photos in the current mobile workflow.
- Correct orientation before provider submission or normalize EXIF orientation server-side.
- Strip unnecessary EXIF GPS and device metadata from durable derivatives.
- Preserve sufficient diagnostic detail; avoid aggressive re-compression.
- Scan uploads for malicious payloads and verify decoded image content.
- Never log raw bytes or signed image URLs.

## 19. Permission-related mobile behavior

- Camera is requested only when the user taps Capture.
- Foreground location is requested only on the location step or map recenter.
- Background location is never requested.
- Permanent denial provides an Open settings action.
- Denied map location does not block viewing registered trees.
- A failed or denied step does not delete the local draft.
- Android uses CAMERA, ACCESS_FINE_LOCATION, and ACCESS_COARSE_LOCATION.
- iOS uses NSCameraUsageDescription and NSLocationWhenInUseUsageDescription.
- Gallery import is not part of the tree-registration workflow; existing social/profile features may still need photo-library descriptions.

## 20. Server-side Kindwise responsibilities

The backend exclusively owns:

- Kindwise API credentials and rotation.
- Provider request shape and image transfer.
- Rate limiting, quotas, retries, and circuit breaking.
- Provider error mapping into the stable codes above.
- Normalizing taxonomy, confidence, descriptions, health, and attribution.
- Licensing checks for representative images and text.
- Retaining provider audit references without exposing raw responses to normal clients.
- Durable image storage, authorization, and deletion policy.

No Kindwise key, provider secret, or direct provider URL may be shipped in Flutter.

## 21. Additional example: no confident identification

~~~json
{
  "id": "analysis_01J5LOW",
  "provider": "kindwise_plant_id",
  "analyzed_at": "2026-08-15T05:00:25.000Z",
  "candidates": [],
  "health": null
}
~~~

This is a successful analysis with no usable match. The user may register the tree as unknown. Use 422 low_confidence only when product rules require analysis to block creation; the current mobile UX prefers the successful empty-candidates form.

## 22. Backend acceptance criteria

- Every endpoint follows this path and field contract or an agreed versioned revision.
- Authentication and ownership are enforced.
- Multipart categories remain correctly associated with files.
- Location evidence is persisted without exaggerating precision.
- Analysis returns provider-neutral candidates and never exposes credentials.
- Empty and nullable provider data serialize safely.
- Nearby search is geospatial, distance-sorted, and never auto-merges.
- Tree creation is idempotent across delayed responses and retries.
- The immutable AI result and user choice are both retained.
- Health is null unless actually assessed.
- Tree list supports cursor pagination and required sorts explicitly.
- Full tree details and scans match their schemas.
- Stable error codes and request IDs are implemented.
- Automated backend tests mock Kindwise and never consume live credits.
- Contract tests cover timeouts, quota, invalid images, low confidence, nearby empty/results, and duplicate submission retry.

## 23. Differences from current repository behavior

Before this mobile upgrade, the repository:

- Uploaded three images separately and called POST /trees/register.
- Used front, trunk, and leaves image keys without normalized analysis.
- Took one current-position reading rather than multi-sample evidence.
- Generated an idempotency key at submission time, so a retry could change it.
- Read GET /trees/map and GET /trees/{id}/timeline.
- Used raw tree status as a proxy for health.
- Expected some list endpoints to return a bare JSON list.

The new implementation uses the contract in this document. Legacy TreeApiService remains temporarily for unrelated existing code, but the core Home, Map, My Trees, details, and registration flow depend on TreeRepository and the new endpoints. The backend team should implement the new contract rather than extending the legacy /trees/register payload.
